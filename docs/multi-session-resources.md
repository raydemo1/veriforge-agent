# 多会话资源管理验收

2026-11-03，Windows，本地基线 `b409d0d`。

## 执行方式

会话按需初始化，连续空闲 120 秒后自动释放运行时。只切换标签不会唤醒或休眠；排队消息、审批、子代理、后台 Shell、未完成工具和未结束的 MCP 执行都会阻止休眠。唤醒保留会话 ID、消息、草稿和界面状态，休眠不记录为用户结束会话。Worktree 仍只由用户主动创建。

项目内的模型额度复用 `MAX_CONCURRENT_AGENTS`，当前默认 3；子代理使用同样上限的共享线程池，工具共享 8 个工作线程，网络与 MCP 连接各 2 个额度，每个 MCP 服务调用并发为 2。额度跟随真实执行退出释放，等待可取消；资源等待不计入 MCP 的实际连接和调用超时。审批不持有模型额度。

MCP 配置和 Schema 缓存按项目与配置区分，每个会话保留自己的连接。资源面板关闭时不采样进程树；打开后每秒显示后台进程内存和 CPU 累计时间。Trace 按会话和 Agent 实例分别写入，不再回落到源码目录。

## 一次性资源测量

每个会话数在独立 Python 进程中测量真实 BridgeServer / InteractiveSession。模型替身只返回确定的流式内容，没有远程模型请求；关闭记忆生成、未配置外部 MCP。基线和改后分别测量，数值为单次观测，不是统计置信区间。性能脚本与原始日志保存在本地 `.harness/third-batch/`，不加入长期测试。

首会话启动和常驻线程显著减少；批量新建 10 个会话的时间没有改善，元数据和历史仍逐个处理。按需初始化延后了首次使用成本，没有消除这部分工作。强制逐个唤醒所有会话的耗时分别为 700.71 ms、2183.53 ms、3248.56 ms、7141.55 ms；不能与原来并行初始化全部会话的墙钟时间直接比较。

以上冷会话 RSS 采样在执行模型替身前。执行后会首次加载分词器等共享缓存，进程 RSS 不会随休眠全部归还给系统；因此不把休眠后的 RSS 当作已释放会话内存的证据。所有场景在未使用 MCP 时服务子进程数为 0；真实双会话 stdio 验证中，目录缓存不会启动进程，实际调用分别建立连接，计数器状态彼此独立。
