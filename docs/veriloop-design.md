# VeriLoop：内外双环协同进化的 Coding Agent（设计方案）

> 状态：方案 / 待评审。本文规划项目更名为 VeriLoop 之后的核心特性，不代表已实现的行为。

## 0. 一句话

**VeriLoop = Verify + Loop。内环在单次运行里用客观门禁当场消灭低级错误；外环跨运行从失败中学习，并反过来改写内环的门禁。两个环用同一本账本、同一个适应度协同进化。最终交付物是：在 DeepSeek-V4.1-Flash-1017 上，Terminal-Bench 4.1 的 20 题子集上一组可复现、可归因的提升数字，以及低级错误类失败的归零。**

面试时的叙事主线：

1. 已有工作要么只做单次运行内的自我修正（Reflexion、验证器重试），要么只做跨运行的 Harness 进化（AHE、Self-Harness、RRSI、Meta-Harness），**很少有人让两者互相塑造**。
2. 只有内环，规则写死了就不会变，而且我们自己的数据显示它的误报很多（见 §2）。只有外环，学到的经验大多停在提示词里，模型可能不遵守。
3. VeriLoop 的关键做法是**知识硬化**：外环学到的经验，如果其失效条件能被客观检测，就被「编译」成内环的可执行探针，从软约束变成硬约束。内环的每次拦截又天然产生「拦截前失败、拦截后是否修好」的反事实标签，反过来训练外环。
4. 用 RRSI 的正则化防止外环在评测集上过拟合，用 ECC 的 instinct 置信度管理未硬化的经验，最后在 held-out 上拿到干净的提升。
5. **评测成本跟着改动的影响范围走，不跟着基准规模走**：所有改动都是条件触发的，所以可以离线算出哪些试验会受影响，能从结束点续跑就不重跑。整个进化过程控制在约 2 次全量评测的成本以内（§8）。

## 2. 出发点：现有数据说明了什么

**模型已经换代，旧基线作废**。项目账本里的 56/89（62.9%）是 DeepSeek-V4-Flash-Preview 在 TB2.1 上的成绩。DeepSeek API 的 `deepseek-flash` 已经在 2026-10-17 静默升级为 **DeepSeek-V4.1-Flash-1017**，模型名没变，所以旧数据不能直接用，基线必须重跑（见 §8.0 的数据集选择）。

**这个模型在各基准上的公开成绩**（2026-11-19 查询）：

| 基准 | 成绩 | 来源与配置 | 剩余空间 |
| --- | --- | --- | --- |
| Terminal-Bench 2.1 | 90.6（V4.1-Flash-0910；1017 没有再报告） | DeepSeek 官方 | **几乎饱和** |
| Terminal-Bench 4.0 | 42.3 | DeepSeek 官方，Claude Code 框架 | 大 |
| Terminal-Bench 4.0 | 40.00 | benchlm，max 档 | 大 |
| Terminal-Bench 4.1 | **38.48** | benchlm，Claude Code，max 档 | 大 |
| Terminal-Bench 4.0 | **31.82**（每题 0.54 美元、约 41 分钟） | Vals，mini-swe-agent（只有 bash 工具），3 次平均 | 大 |
| DeepSWE v1.1 | 77.0 | DeepSeek 官方，Mini-SWE-V2 | 中 |
| NL2Repo-Bench | 68.2 | DeepSeek 官方 | 中 |

最关键的一点是：**同一个模型，换一个 Harness，TB4 的成绩就在 31.8（mini-swe-agent）到 38.5–42.3（Claude Code）之间浮动**，差距约 7–10 个点。这说明在这个模型上，Harness 本身就是主要变量，自进化有足够的发挥空间。同类工作的参照：AHE 在 TB2 上进化 10 轮，从 69.7% 到 77.0%；Self-Harness 在三个模型上提升了 10–20 个点。

**现有内环的问题**（`eval/results/verifier-ablation-20261109-082001-253803`，3 道简单 Python 任务 × 2 次重复）：

| 组 | 通过 | 成本（美元） | LLM 调用 | 干预次数 | 其中干预前已经能通过 |
| --- | --- | --- | --- | --- | --- |
| A 关闭验证器 | 6/6 | 0.0385 | 53 | 0 | 0 |
| B 只记录 | 6/6 | 0.0289 | 48 | 0 | 0 |
| C 当前退出门禁 | 6/6 | 0.0678 | 82 | 4 | **4** |

4 次干预全是误报（例如 Ruff 的 `EXE002`「文件可执行但没有 shebang」），成本比关闭验证器高 76%，没有带来任何正确性收益。样本很小，但方向很清楚：**一个写死的内环门禁会在没有失败的地方持续制造成本**，必须有一个外部机制来衡量每条检查的精确率，并据此剪枝和补充。这就是外环要做的事。

## 4. 总体架构

```text
              ┌───────────── 外环：跨运行进化（离线 / 空闲时） ─────────────┐
              │  ① 观测汇总 → ② 失败签名挖掘 → ③ 提案（带 RRSI 正则）         │
              │  → ④ 门禁回放（evolve 集 + held-out + 成本）→ ⑤ 发布 / 剪枝    │
              │                                                            │
              │    知识硬化阶梯：观察 → instinct → playbook 条目 → 内环探针    │
              └──────▲─────────────────────────────────────────┬──────────┘
   干预记录（反事实标签）│                                         │ 探针集 vN / playbook vN
   未拦住的失败         │                                         ▼
              ┌──────┴──────────── 内环：单次运行内的客观门禁 ──────────────┐
              │ 编辑后 / 命令后 / 结束前 → 探针按触发条件运行 → 客观判定        │
              │   通过 → 继续          失败 → 注入纠正、限次重入、记录前后状态    │
              └────────────────────────────────────────────────────────────┘
  可信根（两个环都改不了）：判题测试 · 评测切分 · 门禁代码 · 权限 / 沙箱 · 账本
```

两条硬约束：

- **会话内版本固定**。内环探针集和 playbook 在会话开始时载入，会话中途不变，保持系统提示前缀稳定和 KV Cache 命中。
- **改动必须条件触发、局部生效**。所有可进化产物都只在触发条件命中时才起作用，不改常驻系统提示。这既保证缓存命中，也让评测可以增量进行（§8.1）。
- **修改者不能修改验证器**。外环可以增删探针，但探针的执行器、判题测试和门禁规则属于可信根。产物写在状态根下，Agent 本身不能写状态根，这条现有不变量直接复用。

## 5. 内环：客观门禁（单次运行）

### 5.1 探针（Probe）

内环由一组**探针**组成。每个探针是一条声明式规则，由受信任的通用中间件执行，不允许包含任意 Python 代码：

```yaml
id: probe.deliverable_exists
trigger: before_finish                 # after_edit | after_command | before_finish
applies_if: task_mentions_output_paths # 客观前提，不满足就不运行
check: all_paths_exist                 # 内置检查原语，带参数
on_fail:
  message: "任务要求的输出文件 {missing} 还不存在。先生成它，再结束。"
  max_reentries: 2
status: active                         # shadow | active | retired
origin: seed                           # seed | evolved:chg-0031
```

检查原语是有限的、可信的集合：

- 文件和路径：存在、非空、能解析为 JSON/YAML、匹配给定 schema。
- 命令：重跑某条命令并检查退出码；判断「最近一次测试或构建命令的退出码」。
- 进程和端口：进程存活、端口在监听、HTTP 能响应。
- 静态检查：**按 diff 计算**，只看本次运行新引入的问题。
- 过程事实：同一失败指纹重复的次数、编辑之前是否读过目标文件。

外环只能组合这些原语、调整参数，不能新增原语。新增原语需要人写代码并评审。

### 5.2 种子探针

先从「低级错误」做起：判定完全客观，修复成本低，模型一被提醒就能修好。第一版种子集（P0 的失败分类会验证和调整这份清单）：

| 探针 | 触发时机 | 消灭的低级错误 |
| --- | --- | --- |
| `deliverable_exists` | 结束前 | 任务要求的输出文件、目录没生成，或生成的路径不对 |
| `last_check_green` | 结束前 | 最近一次测试或构建命令失败了，却声称完成 |
| `new_static_errors` | 编辑后 | 本次改动新引入的语法、类型、未定义名错误（按 diff，排除 `EXE002` 这类风格噪声） |
| `service_alive` | 结束前 | 声称服务已启动，实际进程已退出或端口没监听 |
| `env_persisted` | 结束前 | 依赖安装在子 shell 或临时虚拟环境里，判题环境里看不到 |
| `failure_loop` | 命令后 | 同一错误指纹连续出现 N 次仍在原地重试（与 `tool_failure_policy` 合并，不重复实现） |

### 5.3 干预协议

- **限次重入**：每个探针每次运行最多重入 `max_reentries` 次，内环总干预次数也有上限，不会无限拖住回合。
- **每次干预都记录三个事实**：触发时的客观状态、干预前的判题结果（评测里可以在隔离副本上预跑隐藏测试；产品里用 `last_check_green` 的状态近似）、干预后的状态。这正是现有消融里 `first_intervention_already_passing` 和 `failed_before_intervention_passed_after` 这两个字段的推广。
- **影子模式**：新探针先以 `shadow` 状态上线，只记录「本来会触发」，不干预、不花模型调用，攒够精确率证据才转为 `active`。

## 6. 外环：跨运行进化

### 6.1 观测

参考 ECC：在已有的中间件钩子（`before_tool`、`post_tool`、`on_tool_failure`、对话结束）上做 100% 观测，不依赖模型自觉调用。每个回合结束追加一个 `outcome` 事件：判题结果、停止原因、探针触发与干预记录、token 和耗时。

### 6.2 失败签名挖掘

按 Self-Harness 的确定性三元组聚类：`(判定层原因, Agent 行为是否有因果贡献, 抽象机制)`。例如 `(output_missing, yes, wrote-to-wrong-path)`。

- 按支持度和可行动性排序，只输出证据包，**不给修改方案**。
- 每条证据附原始轨迹定位（会话、回合、`tool_call_id`），提案器可以下钻读原文（Meta-Harness 的结论：原始轨迹比摘要有用）。
- 明显属于任务太难或模型能力不足的簇直接排除。

### 6.3 知识硬化阶梯（核心创新）

外环的每一条经验都在一条阶梯上，**载体由「能否客观检测」决定，而不是由提案器的喜好决定**：

| 层级 | 载体 | 进入条件 | 生效方式 |
| --- | --- | --- | --- |
| L0 观察 | 原始事件 | 自动 | 不生效 |
| L1 instinct | ECC 式原子条目：触发、动作、证据、置信度 0.3–0.9、作用域（项目 / 全局） | 同一签名出现 ≥ 2 次 | 置信度 ≥ 0.5 且触发条件命中时，以运行时消息注入 |
| L2 playbook 条目 | ACE 式条目，带稳定 ID 和 helpful/harmful 计数 | 通过外环门禁 | 触发条件命中时以运行时消息注入；没有触发条件的通用条目才进启动快照（固定 token 预算） |
| L3 内环探针 | §5.1 的声明式探针 | 失效条件能用现有原语客观检测，且通过外环门禁 | 运行中强制执行 |

- **向上硬化**：L2 条目如果「被加载了，但轨迹显示模型没遵守，失败依旧」，而它描述的失效条件又能客观检测，外环就提议把它硬化为 L3 探针。这是第 9 章「同一问题该放在哪个载体」的自动化回答。
- **向下软化与淘汰**：L3 探针精确率持续偏低（干预前大多已经能通过），先降级为 `shadow`，再退役。L1/L2 条目 harmful 多于 helpful，或长期未激活，就降低置信度或归档。
- **作用域提升**：沿用 ECC 规则，出现在 2 个以上项目且平均置信度 ≥ 0.8 时，从项目级提升为全局。

### 6.4 提案与 RRSI 正则化

每个提案必须附一份变更契约：证据、根因、改动的组件、diff，以及可证伪的预测（哪些题会翻转为通过、成本变化上限、可能伤到什么）。正则化规则直接借鉴 RRSI：

| 规则 | 做法 | 防的是什么 |
| --- | --- | --- |
| 退火改动预算 | 第 1 代允许一个提案捆绑多处改动，之后逐代收紧到每个提案只改一处 | 后期改动无法归因 |
| 证据感知的信用分配 | 账本记录每个假设的接受或拒绝结果，提案器看得到已被证伪的想法 | 反复重试已失败的方向 |
| 停滞转向 | 连续几代的增益都落在噪声带内时，强制把提案名额分给还没试过的组件或失败簇 | 在一个局部最优上打转 |
| 泄漏审查 | 一个独立的审查器拒绝含有评测任务名、任务特有路径或期望答案的 diff | 把答案写进 Harness |
| 噪声调整下限 | 分数低于历史最好分数减去噪声带的候选直接淘汰 | 噪声中的偶然退步被接受 |
| 成本规则 | token 或耗时的增加必须由实测增益来支付 | 用更多调用换来很小的提升（正是 §2 里的问题） |
| 结构剪枝 | 近 N 代没有正贡献的探针和条目被标记删除 | 规则只增不减、上下文膨胀 |

### 6.5 门禁

在隔离副本上回放，规则如下：

1. evolve 集通过数变化 ≥ 0，held-out 通过数变化 ≥ 0，且至少一边 > 0。只评估 L0 判定会被激活的试验加哨兵题，按 §8.2 的漏斗逐级进行；mini-gym 上便宜，可以每题跑 k 次。
2. 满足 §6.4 的成本规则。
3. **激活归因**：预测会翻转的题，轨迹里必须真的触发了这次改动（探针被触发、条目被加载并被引用），否则当作噪声拒绝。
4. 写入预测账本：预测会翻转的题和实际翻转的题，算精确率和召回率。

## 7. 协同进化：两个环如何互相塑造

| 方向 | 机制 | 例子 |
| --- | --- | --- |
| 外环 → 内环：新增 | 硬化阶梯把可检测的失败簇编译成新探针 | 「写到了错误路径」簇 → `deliverable_exists` 增加对任务描述中绝对路径的解析 |
| 外环 → 内环：剪枝 | 按精确率和成本规则降级或退役探针 | `EXE002` 一类风格告警从 `new_static_errors` 中排除 |
| 外环 → 内环：调参 | 调整触发范围、重入次数 | `failure_loop` 的阈值从 5 降到 3 |
| 内环 → 外环：标签 | 每次干预产生「前后状态」三元组，是免费的反事实标签，直接算出每个探针的精确率和挽救率 | 探针 X 触发 40 次，其中 12 次「干预前失败、干预后通过」 |
| 内环 → 外环：目标 | 内环没拦住的失败，就是外环下一代的挖掘目标 | 所有探针都没触发、但判题失败的题，进入下一轮聚类 |

**统一适应度**：`通过率 − λ · 每题成本`。探针和条目在同一本账本、同一份成本预算里竞争，不论在哪个环生效，都按对适应度的边际贡献计分。

## 8. 评测方案：低成本增量评测（重点）

### 8.0 数据集：Terminal-Bench 4.1 的 20 题子集

只用 TB4.1，不跑全量，也不再用 TB2.1。具体清单、切分和挑选规则在 [`eval/tasks/veriloop_tb41_20task.json`](../eval/tasks/veriloop_tb41_20task.json)。

**为什么只用 TB4.1**：1017 在 TB2.1 上接近饱和（官方 90.6），失败太少，学不到什么。在 TB4.1 全部 66 题上，它每轮大约做对 21–28 道，取决于用哪个 Harness（mini-swe-agent 21 道，Claude Code 约 25.4 道）。剩余空间大，判题器也做过防 reward hacking 的加固。

**挑选规则**（只看 `task.toml`、`environment/Dockerfile` 和 `tests/`，不看任何运行结果）：

| 规则 | 具体做法 |
| --- | --- |
| 能跑 | 不需要 GPU；**任务环境和判题环境都不超过 4 核、8 GB**（因此排除 `medical-claims-processing`、`formal-crypto`、`shadow-relay`，以及判题环境要 8 核 / 16 GB 的 `payments-pipeline-fix`）；排除在 CPU 上部署大模型的题（`sglang-qwen-burst`、`vllm-deepseek-streaming`）和需要 QEMU 虚拟机的 `uefi-bootkit`；网络只在构建镜像时需要 |
| 不要太难 | 按专家估时从短到长取，范围 0.75–4 小时（整个基准的中位数约 4 小时） |
| 覆盖面 | 7 个类别全覆盖：Software 3、Science 3、Hardware 4、Operations 4、Media 2、ML 2、Security 2；排除 `layout-config-recreation2`，因为它是另一道题的变体，分在两边会造成泄漏 |

**切分**：evolve 10 题、held-out 10 题，按类别分层，两边的专家估时总量接近（22.75 小时对 20.25 小时）。

**挑选只用元数据**：如果先跑一遍、再专挑失败的题，那么重跑时，即使什么都不改，分数也会因为回归均值而「上涨」。所以这 20 道题是在任何运行之前就冻结的。替补题是 `nextjs-performance`、`sound-change-cascade`、`risk-scorer-replay`、`gsea-proteomics`，只在题目本身跑不起来时才替换（镜像构建失败、判题基础设施不可用），而且必须在看到 Agent 结果之前决定。

**难度的局限**：Harbor Hub 上公开的逐题通过率是页面在浏览器里动态加载的，这次没取到，所以「不要太难」目前只靠专家估时来近似。P0 跑完基线后，如果某道题明显是谁都做不出来的，只在报告里标注，不事后替换。

**模型档位与次数**：1017 开思考的 `normal` 档（`reasoning_effort=high`）。**每题只跑 1 次**；Agent 预算每题 3600 秒（官方超时是 8 小时，所以结果不能和排行榜直接比较）。

**成本估算**（尚未实测，P0 会给出真实数字）：

- 专家估时 0.75–3.5 小时的题，Agent 实际耗时预计 15–40 分钟。Vals 在全部 66 题上的平均值是 41 分钟、0.54 美元，这 20 道是最短的，应低于这个数。
- 跑一遍 20 题预计 5–10 美元。在 6 核 / 6 GB 的机器上并发只能是 1，预计 6–10 小时。

**资源**：已排除所有需要 16 GB 或 8 核的题。仍有 7 道题声明了 8 GB 内存，`intrastat-meldung` 和 `legacy-utility-triage` 还会启动额外的服务容器；在 6 GB 的机器上要观察是否 OOM。`html-js-filter` 的判题镜像是针对 Modal 调过的，P0 要先确认本地 Docker 能跑，跑不了就在看到 Agent 结果之前用替补题替换。

**P0 要先确认的两件事**：

- TB4 的判题器都在独立镜像里运行（`environment_mode = "separate"`），要确认 Harbor 在本地 Docker 下能正常跑。
- 适配器已接入 TB4.1：`python eval/scripts/run_terminal_bench_eval.py --tbench-task-set tb41-20task`（用法见 `eval/README.md`）。

其他约定：

- 基线、各代和最终版本使用同样的档位和任务默认超时。
- **锁定模型版本**：`deepseek-flash` 会在不改名的情况下升级。每次运行都把 API 返回的模型标识和日期写入产物；基线和最终运行之间如果模型换了，必须重跑基线。
- **对外的说法统一为「TB4.1 的 20 题子集」**，不能当成 TB4.1 全量成绩来报告。

### 8.1 原则：成本跟着「改动影响的范围」走，不跟着基准规模走

完整跑一遍 20 题子集（下称 **1 个全量单位**）虽然不贵，但每代都跑仍然浪费。下面三条设计让大部分评测变成增量的：

1. **改动必须是条件触发、局部生效的**。探针只在触发条件满足时才干预。instinct 和 playbook 条目也一样：不常驻系统提示，只在触发条件命中时以运行时消息注入（§6.3）。一个改动如果在某次试验里没有触发，这次试验的行为就完全不变，也就不用重跑。
2. **先离线算出哪些试验会受影响**。触发条件都是轨迹上的客观事实，可以直接在已有轨迹上计算，不需要调用模型。
3. **能续跑就不重跑**。「结束前」触发的探针不会改变结束之前的任何轨迹，所以从结束点的快照续跑，和从头完整重跑是等价的。

### 8.2 四级评测漏斗

| 级别 | 做法 | 模型成本 | 用途 |
| --- | --- | --- | --- |
| **L0 离线回放** | 在已有的轨迹（会话日志、Trace、Harbor 判题输出）上，计算每个候选探针或条目会在哪些试验里触发。在失败试验上触发的是潜在挽救；在通过试验上触发的是误报风险 | 0，秒级 | 外环挖掘；在花钱之前筛掉绝大多数候选 |
| **L1 结束点续跑** | 每次试验在 Agent 结束、判题之前，导出会话并给容器做快照。评估「结束前」探针时，只挑 L0 判定会触发的试验：恢复容器和会话，注入探针消息，限额续跑（例如最多 8 次工具调用），然后判题 | 只付续跑那一小段的钱；前缀和原会话一致，大部分输入能命中缓存 | 内环探针的挽救率和破坏率 |
| **L2 定向重跑** | 只从头重跑 L0 判定会被激活的试验，外加几道固定的哨兵题（约 4 道已经通过、对改动敏感的题） | 每代约 0.2–0.4 个全量单位 | 运行中途触发的探针、instinct 和条目 |
| **L3 里程碑全量** | 只在最后对最终版本跑 20 题，每题 1 次 | 1 个全量单位 | 面试的头条数字 |

另外建一个**本地 mini-gym**：约 30 道按 20 题基线的失败类别仿写的本地夹具任务，例如输出路径、环境持久化、服务存活、收尾时测试未通过。它复用 `dev_tasks_v1` 的隐藏测试加 golden 机制，每题 20–40 秒、约 0.005 美元，全套几分钟、几毛钱。它作为外环每一代的快速回归，消融实验也主要在这里做。

**快照的实现**：`HarnessAgent.run()`（`eval/benchmarks/harbor_agent.py`）返回之后 Harbor 才开始判题，所以在 `run()` 返回前加一个快照钩子即可：从宿主机侧 `docker commit`，或在容器内打包工作目录。会话本身已经由 `hca_terminal_runner.py` 完整导出。局限是快照只保存文件系统，不保存运行中的进程，所以依赖后台服务的探针（例如 `service_alive`）不能用 L1 评估，归到 L2。

### 8.3 成本对比

| 方案 | 全量单位（估算） |
| --- | --- |
| 原方案：4 个臂 × 每题 3 次 × 每代全量 | ≥ 12，并且随代数增长 |
| 新方案：基线 1 次 + L0 + L1 + 3–5 代 L2 + 最终 1 次 | 约 3–3.5 个全量单位，1 个单位只有 20 题；粗估总花费在 15–35 美元量级（估计值，以 P0 实测为准）；对比 TB4.1 全量方案约 100 美元 |

### 8.4 消融不再跑四臂全量

- **B 臂（只开内环）不需要额外运行**：它的 20 题数字由 L1 直接推算，等于基线加上种子探针挽救的题、减去被它破坏的题。
- **C 臂和 D 臂的对比**放在 mini-gym 和 L2 子集上做。
- **全量只取两个点**：基线和最终版本，各跑 1 次。

### 8.5 用「激活归因」对付噪声

题集很小、每题只跑 1 次，单题翻转可能只是随机性。最终报告把所有翻转的题分成两类：

- **已归因翻转**：轨迹里有某个探针或条目被触发，而且翻转方向和变更契约的预测一致。
- **未归因翻转**：没有任何改动被激活，题目却翻转了，这只能是运行间的随机噪声。

没被激活的题天然就是**噪声对照组**：它们的翻转率直接估计了运行间噪声，不需要额外重复。头条只报告**已归因的净提升**，同时给出对照组的翻转率作为误差参照。这个结论比「两次总分相减」更强，也更难被质疑。

### 8.6 切分与防止自欺

- 切分在任何运行之前就已冻结（§8.0），只依据元数据，不依据基线结果。
- **提案器只看得到 evolve 集的轨迹**。门禁可以用 held-out 的汇总结果，但提案器看不到其中的任何内容。最终报告分两个子集列出，头条用 held-out。
- 切分和判题测试计算哈希后写入产物。泄漏审查器之外，最终保留的每一条改动都要人工过一遍。
- 被拒的提案、退役的探针、中断的运行全部保留在账本里，并在报告中列出。

### 8.7 指标与目标

| 指标 | 说明 | 目标（是目标，不是承诺） |
| --- | --- | --- |
| held-out 已归因净提升 | 头条 | 净挽救 2–3 题（10 题里每题 10 个点） |
| 20 题整体 | 两次运行的平均通过率 | 相对基线净挽救 4–6 题 |
| 低级错误失败数 | 失败题中属于种子探针覆盖类别的题数 | 接近 0 |
| 探针精确率、挽救率、破坏率 | 来自 L1 | 破坏率接近 0 |
| 提案接受率、预测精确率 | 外环账本 | — |
| 每次成功的成本 | 与基线对比 | 不高于基线 |
| **整个进化过程的总花费** | 美元和全量单位 | 约 5–6 个全量单位，在报告中明示 |

### 8.8 面试展示物

1. 一张主表：1017 上基线和进化后的结果，分 evolve 和 held-out 两部分；附每次成功的成本；标出已归因翻转和噪声对照组。可以在旁边注明 1017 在 TB4.1 全量上的公开参照（Claude Code 38.48、mini-swe-agent 31.82），但明确说明不能直接比较。
2. 评测漏斗图：每一级筛掉多少候选、花了多少钱，用来说明「为什么这样做便宜」。
3. 失败类别的前后对比瀑布图：哪些失败被哪个环消灭了。
4. 一个完整的硬化案例：从失败簇到 instinct、条目、探针，附每一步的证据和数字。

| 阶段 | 内容 | 额外的全量成本 | 产出 | 估时 |
| --- | --- | --- | --- | --- |

## 10. 风险

| 风险 | 缓解 |
| --- | --- |
| 统计噪声：10 题的 held-out 上，单题翻转就是 10 个点 | 头条只报已归因的翻转，用未激活的题作噪声对照组（§8.5）；不夸大 |
| L1 续跑和完整重跑不等价 | 只对「结束前」触发的探针用 L1；中途触发的和依赖进程状态的走 L2 |
| 对 evolve 集过拟合 | RRSI 正则、held-out 隔离、OOD 检查、泄漏审查 |
| 探针误报拖慢运行 | 影子模式、精确率阈值、成本规则、结构剪枝 |
| 评测成本与时间 | 20 题子集加四级漏斗和 mini-gym；全量只在基线和最终时运行 |
| 子集结果被当成整个基准的成绩 | 对外统一说「TB4.1 的 20 题子集」，公开的全量成绩只作背景参照 |
| 挑题偏差 | 只按元数据挑选并在运行前冻结；替补规则写死在任务文件里 |
| 模型静默升级（`deepseek-flash` 不改名就换版本） | 每次运行记录模型标识；基线和最终运行之间换了版本就重跑基线 |
| 有些失败源于模型能力不足，而不是 Harness 的问题 | P0 的失败分类会给出真实占比；明显属于能力不足的题在挖掘阶段直接排除（§6.2），不当作学习目标 |
| 探针被当作「作弊」 | 检查原语都是通用的，泄漏审查器加人工复核，每条探针在报告中列出来源证据 |
| 产品模式下没有判题器 | P5 的 Repo Gym；在那之前，产品模式只启用内环和人工批准的外环产物 |
