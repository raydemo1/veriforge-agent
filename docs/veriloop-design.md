# VeriLoop：内外双环协同进化的 Coding Agent（设计方案）

> 状态：方案 / 待评审。本文规划项目更名为 VeriLoop 之后的核心特性，不代表已实现的行为。

## 0. 一句话

**VeriLoop = Verify + Loop。内环在单次运行里用客观门禁当场消灭低级错误；外环跨运行从失败中学习，并反过来改写内环的门禁。两个环用同一本账本、同一个适应度协同进化。最终交付物是：在 DeepSeek-V4.1-Flash-1017 上，本地 VeriLoop-Bench（24 道多陷阱任务）held-out 上一组带置信区间、可归因的提升数字，以及低级错误类失败的归零。**

面试时的叙事主线：

1. 已有工作要么只做单次运行内的自我修正（Reflexion、验证器重试），要么只做跨运行的 Harness 进化（AHE、Self-Harness、RRSI、Meta-Harness），**很少有人让两者互相塑造**。
2. 只有内环，规则写死了就不会变，而且我们自己的数据显示它的误报很多（见 §2）。只有外环，学到的经验大多停在提示词里，模型可能不遵守。
3. VeriLoop 的关键做法是**知识硬化**：外环学到的经验，如果其失效条件能被客观检测，就被「编译」成内环的可执行探针，从软约束变成硬约束。内环的每次拦截又天然产生「拦截前失败、拦截后是否修好」的反事实标签，反过来训练外环。
4. 用 RRSI 的正则化防止外环在评测集上过拟合，用 ECC 的 instinct 置信度管理未硬化的经验，最后在 held-out 上拿到干净的提升。
5. **评测要便宜到能重复跑**：主评测是本地的 VeriLoop-Bench，每次运行约 ¥0.05–0.25，四个对照组、每题 3 次总共几十元，从而能报置信区间，而不是靠一次运行的总分（§8）。

## 2. 出发点：现有数据说明了什么

**模型已经换代，旧基线作废**。项目账本里的 56/89（62.9%）是 DeepSeek-V4-Flash-Preview 在 TB2.1 上的成绩。DeepSeek API 的 `deepseek-flash` 已经在 2026-10-17 静默升级为 **DeepSeek-V4.1-Flash-1017**，模型名没变，所以旧数据不能直接用，基线必须重跑（见 §8.0 的数据集选择）。

**这个模型在各基准上的公开成绩**（2026-11-19 查询）：

| 基准 | 成绩 | 来源与配置 | 剩余空间 |
| --- | --- | --- | --- |
| Terminal-Bench 2.1 | 90.6（V4.1-Flash-0910；1017 没有再报告） | DeepSeek 官方 | **几乎饱和** |
| Terminal-Bench 4.0 | 42.3 | DeepSeek 官方，Claude Code 框架 | 大 |
| Terminal-Bench 4.0 | 40.00 | benchlm，max 档 | 大 |
| Terminal-Bench 4.1 | **38.48** | benchlm，Claude Code，max 档 | 大 |
| Terminal-Bench 4.0 | **31.82**（每题 0.54 美元、约 41 分钟） | Vals，mini-swe-agent（只有 bash 工具），3 次平均 | 大 |
| DeepSWE v1.1 | 77.0 | DeepSeek 官方，Mini-SWE-V2 | 中 |
| NL2Repo-Bench | 68.2 | DeepSeek 官方 | 中 |

最关键的一点是：**同一个模型，换一个 Harness，TB4 的成绩就在 31.8（mini-swe-agent）到 38.5–42.3（Claude Code）之间浮动**，差距约 7–10 个点。这说明在这个模型上，Harness 本身就是主要变量，自进化有足够的发挥空间。同类工作的参照：AHE 在 TB2 上进化 10 轮，从 69.7% 到 77.0%；Self-Harness 在三个模型上提升了 10–20 个点。

**现有内环的问题**（`eval/results/verifier-ablation-20261109-082001-253803`，3 道简单 Python 任务 × 2 次重复）：

| 组 | 通过 | 成本（美元） | LLM 调用 | 干预次数 | 其中干预前已经能通过 |
| --- | --- | --- | --- | --- | --- |
| A 关闭验证器 | 6/6 | 0.0385 | 53 | 0 | 0 |
| B 只记录 | 6/6 | 0.0289 | 48 | 0 | 0 |
| C 当前退出门禁 | 6/6 | 0.0678 | 82 | 4 | **4** |

4 次干预全是误报（例如 Ruff 的 `EXE002`「文件可执行但没有 shebang」），成本比关闭验证器高 76%，没有带来任何正确性收益。样本很小，但方向很清楚：**一个写死的内环门禁会在没有失败的地方持续制造成本**，必须有一个外部机制来衡量每条检查的精确率，并据此剪枝和补充。这就是外环要做的事。

## 4. 总体架构

```text
              ┌───────────── 外环：跨运行进化（离线 / 空闲时） ─────────────┐
              │  ① 观测汇总 → ② 失败签名挖掘 → ③ 提案（带 RRSI 正则）         │
              │  → ④ 门禁回放（evolve 集 + held-out + 成本）→ ⑤ 发布 / 剪枝    │
              │                                                            │
              │    知识硬化阶梯：观察 → instinct → playbook 条目 → 内环探针    │
              └──────▲─────────────────────────────────────────┬──────────┘
   干预记录（反事实标签）│                                         │ 探针集 vN / playbook vN
   未拦住的失败         │                                         ▼
              ┌──────┴──────────── 内环：单次运行内的客观门禁 ──────────────┐
              │ 编辑后 / 命令后 / 结束前 → 探针按触发条件运行 → 客观判定        │
              │   通过 → 继续          失败 → 注入纠正、限次重入、记录前后状态    │
              └────────────────────────────────────────────────────────────┘
  可信根（两个环都改不了）：判题测试 · 评测切分 · 门禁代码 · 权限 / 沙箱 · 账本
```

两条硬约束：

- **会话内版本固定**。内环探针集和 playbook 在会话开始时载入，会话中途不变，保持系统提示前缀稳定和 KV Cache 命中。
- **改动必须条件触发、局部生效**。所有可进化产物都只在触发条件命中时才起作用，不改常驻系统提示。这既保证缓存命中，也让评测可以增量进行（§8.1）。
- **修改者不能修改验证器**。外环可以增删探针，但探针的执行器、判题测试和门禁规则属于可信根。产物写在状态根下，Agent 本身不能写状态根，这条现有不变量直接复用。

## 5. 内环：客观门禁（单次运行）

### 5.1 探针（Probe）

内环由一组**探针**组成。每个探针是一条声明式规则，由受信任的通用中间件执行，不允许包含任意 Python 代码：

```yaml
id: probe.deliverable_exists
trigger: before_finish                 # after_edit | after_command | before_finish
applies_if: task_mentions_output_paths # 客观前提，不满足就不运行
check: all_paths_exist                 # 内置检查原语，带参数
on_fail:
  message: "任务要求的输出文件 {missing} 还不存在。先生成它，再结束。"
  max_reentries: 2
status: active                         # shadow | active | retired
origin: seed                           # seed | evolved:chg-0031
```

检查原语是有限的、可信的集合：

- 文件和路径：存在、非空、能解析为 JSON/YAML、匹配给定 schema。
- 命令：重跑某条命令并检查退出码；判断「最近一次测试或构建命令的退出码」。
- 进程和端口：进程存活、端口在监听、HTTP 能响应。
- 静态检查：**按 diff 计算**，只看本次运行新引入的问题。
- 过程事实：同一失败指纹重复的次数、编辑之前是否读过目标文件。

外环只能组合这些原语、调整参数，不能新增原语。新增原语需要人写代码并评审。

### 5.2 种子探针

先从「低级错误」做起：判定完全客观，修复成本低，模型一被提醒就能修好。第一版种子集（P0 的失败分类会验证和调整这份清单）：

| 探针 | 触发时机 | 消灭的低级错误 |
| --- | --- | --- |
| `deliverable_exists` | 结束前 | 任务要求的输出文件、目录没生成，或生成的路径不对 |
| `last_check_green` | 结束前 | 最近一次测试或构建命令失败了，却声称完成 |
| `new_static_errors` | 编辑后 | 本次改动新引入的语法、类型、未定义名错误（按 diff，排除 `EXE002` 这类风格噪声） |
| `service_alive` | 结束前 | 声称服务已启动，实际进程已退出或端口没监听 |
| `env_persisted` | 结束前 | 依赖安装在子 shell 或临时虚拟环境里，判题环境里看不到 |
| `failure_loop` | 命令后 | 同一错误指纹连续出现 N 次仍在原地重试（与 `tool_failure_policy` 合并，不重复实现） |

### 5.3 干预协议

- **限次重入**：每个探针每次运行最多重入 `max_reentries` 次，内环总干预次数也有上限，不会无限拖住回合。
- **每次干预都记录三个事实**：触发时的客观状态、干预前的判题结果（评测里可以在隔离副本上预跑隐藏测试；产品里用 `last_check_green` 的状态近似）、干预后的状态。这正是现有消融里 `first_intervention_already_passing` 和 `failed_before_intervention_passed_after` 这两个字段的推广。
- **影子模式**：新探针先以 `shadow` 状态上线，只记录「本来会触发」，不干预、不花模型调用，攒够精确率证据才转为 `active`。

## 6. 外环：跨运行进化

### 6.1 观测

参考 ECC：在已有的中间件钩子（`before_tool`、`post_tool`、`on_tool_failure`、对话结束）上做 100% 观测，不依赖模型自觉调用。每个回合结束追加一个 `outcome` 事件：判题结果、停止原因、探针触发与干预记录、token 和耗时。

### 6.2 失败签名挖掘

按 Self-Harness 的确定性三元组聚类：`(判定层原因, Agent 行为是否有因果贡献, 抽象机制)`。例如 `(output_missing, yes, wrote-to-wrong-path)`。

- 按支持度和可行动性排序，只输出证据包，**不给修改方案**。
- 每条证据附原始轨迹定位（会话、回合、`tool_call_id`），提案器可以下钻读原文（Meta-Harness 的结论：原始轨迹比摘要有用）。
- 明显属于任务太难或模型能力不足的簇直接排除。

### 6.3 知识硬化阶梯（核心创新）

外环的每一条经验都在一条阶梯上，**载体由「能否客观检测」决定，而不是由提案器的喜好决定**：

| 层级 | 载体 | 进入条件 | 生效方式 |
| --- | --- | --- | --- |
| L0 观察 | 原始事件 | 自动 | 不生效 |
| L1 instinct | ECC 式原子条目：触发、动作、证据、置信度 0.3–0.9、作用域（项目 / 全局） | 同一签名出现 ≥ 2 次 | 置信度 ≥ 0.5 且触发条件命中时，以运行时消息注入 |
| L2 playbook 条目 | ACE 式条目，带稳定 ID 和 helpful/harmful 计数 | 通过外环门禁 | 触发条件命中时以运行时消息注入；没有触发条件的通用条目才进启动快照（固定 token 预算） |
| L3 内环探针 | §5.1 的声明式探针 | 失效条件能用现有原语客观检测，且通过外环门禁 | 运行中强制执行 |

- **向上硬化**：L2 条目如果「被加载了，但轨迹显示模型没遵守，失败依旧」，而它描述的失效条件又能客观检测，外环就提议把它硬化为 L3 探针。这是第 9 章「同一问题该放在哪个载体」的自动化回答。
- **向下软化与淘汰**：L3 探针精确率持续偏低（干预前大多已经能通过），先降级为 `shadow`，再退役。L1/L2 条目 harmful 多于 helpful，或长期未激活，就降低置信度或归档。
- **作用域提升**：沿用 ECC 规则，出现在 2 个以上项目且平均置信度 ≥ 0.8 时，从项目级提升为全局。

### 6.4 提案与 RRSI 正则化

每个提案必须附一份变更契约：证据、根因、改动的组件、diff，以及可证伪的预测（哪些题会翻转为通过、成本变化上限、可能伤到什么）。正则化规则直接借鉴 RRSI：

| 规则 | 做法 | 防的是什么 |
| --- | --- | --- |
| 退火改动预算 | 第 1 代允许一个提案捆绑多处改动，之后逐代收紧到每个提案只改一处 | 后期改动无法归因 |
| 证据感知的信用分配 | 账本记录每个假设的接受或拒绝结果，提案器看得到已被证伪的想法 | 反复重试已失败的方向 |
| 停滞转向 | 连续几代的增益都落在噪声带内时，强制把提案名额分给还没试过的组件或失败簇 | 在一个局部最优上打转 |
| 泄漏审查 | 一个独立的审查器拒绝含有评测任务名、任务特有路径或期望答案的 diff | 把答案写进 Harness |
| 噪声调整下限 | 分数低于历史最好分数减去噪声带的候选直接淘汰 | 噪声中的偶然退步被接受 |
| 成本规则 | token 或耗时的增加必须由实测增益来支付 | 用更多调用换来很小的提升（正是 §2 里的问题） |
| 结构剪枝 | 近 N 代没有正贡献的探针和条目被标记删除 | 规则只增不减、上下文膨胀 |

### 6.5 门禁

在隔离副本上回放，规则如下：

1. evolve 集通过数变化 ≥ 0，held-out 通过数变化 ≥ 0，且至少一边 > 0。在 VeriLoop-Bench 上每题跑 k 次，先用 L0 离线回放筛掉不会被激活的候选（§8.3）。
2. 满足 §6.4 的成本规则。
3. **激活归因**：预测会翻转的题，轨迹里必须真的触发了这次改动（探针被触发、条目被加载并被引用），否则当作噪声拒绝。
4. 写入预测账本：预测会翻转的题和实际翻转的题，算精确率和召回率。

## 7. 协同进化：两个环如何互相塑造

| 方向 | 机制 | 例子 |
| --- | --- | --- |
| 外环 → 内环：新增 | 硬化阶梯把可检测的失败簇编译成新探针 | 「写到了错误路径」簇 → `deliverable_exists` 增加对任务描述中绝对路径的解析 |
| 外环 → 内环：剪枝 | 按精确率和成本规则降级或退役探针 | `EXE002` 一类风格告警从 `new_static_errors` 中排除 |
| 外环 → 内环：调参 | 调整触发范围、重入次数 | `failure_loop` 的阈值从 5 降到 3 |
| 内环 → 外环：标签 | 每次干预产生「前后状态」三元组，是免费的反事实标签，直接算出每个探针的精确率和挽救率 | 探针 X 触发 40 次，其中 12 次「干预前失败、干预后通过」 |
| 内环 → 外环：目标 | 内环没拦住的失败，就是外环下一代的挖掘目标 | 所有探针都没触发、但判题失败的题，进入下一轮聚类 |

**统一适应度**：`通过率 − λ · 每题成本`。探针和条目在同一本账本、同一份成本预算里竞争，不论在哪个环生效，都按对适应度的边际贡献计分。

## 8. 评测方案：本地 VeriLoop-Bench 为主，TB4.1 为可选旁证（重点）

### 8.0 为什么不用 Terminal-Bench 做主评测

TB4.1 每题约 ¥2、几十分钟，还依赖 Docker 环境和独立判题镜像；20 题跑一圈要 ¥40，且只能每题跑 1 次，没法报置信区间。所以主评测换成本地题集，TB4.1 的 20 题子集（`eval/tasks/veriloop_tb41_20task.json`）保留为可选的外部旁证，只在预算允许时跑基线和最终版本各一次。

### 8.1 VeriLoop-Bench

**早期草稿测出了天花板**：最早的一版是 30 道单陷阱小题，要求都写在提示词或文档字符串里。用 DeepSeek-V4.1-Flash-1017 关思考档每题跑 2 次，结果是 **58/60，held-out 30/30**。失败的 2 次恰好都只挂在陷阱检查上，说明判定口径是准的，但基线几乎没有失败可救，测不出提升，所以这版已删除。

**现在的 VeriLoop-Bench**（`eval/tasks/veriloop_bench_v1.py`）的难度来自真实项目里低级错误的成因，而不是靠出偏题：

- **3 个共享的基础项目**：库存 CLI `stockroom`、SQLite 记账库 `ledgerlite`、通知 CLI `notifykit`，各约 15 个文件，带现有测试、文档和 CHANGELOG。
- **约定只写在 CONTRIBUTING.md 和现有代码里**：比如 CHANGELOG 的写法、命令或渠道要注册并写文档、stdout/stderr 与退出码、默认值的位置、金额必须用 Decimal、公开 API 要导出、改表要用新迁移、先校验全部再投递。README 提示改动前先读 CONTRIBUTING，**任务提示词只描述功能**。
- **每题 2–4 个陷阱检查**，名字里带类别（`test_trap_<类别>_...`），报告能按类别统计掉进陷阱的比例。
- **校验更严**：近似解只实现功能，必须通过全部核心检查、挂掉**全部**陷阱检查；golden 还要保持项目自带的 `tests/` 通过；近似解的失败经检查不含 `NameError`、导入错误这类偶然原因。除两道「验证不足」题外，其余 22 题的近似解都能通过项目自带测试，也就是说，这些陷阱靠跑现有测试发现不了。
- **切分**：evolve 12 题、held-out 12 题，每个项目各 4 题。题目在任何运行和探针之前冻结。
- **成本**：项目更大，估计每次运行约 ¥0.1–0.5，待实测。

### 8.2 对照与统计

| 组 | 内环 | 外环 | 回答的问题 |
| --- | --- | --- | --- |
| A 基线 | 关 | 关 | 当前水平 |
| B 只开内环 | 种子探针，固定 | 关 | 静态门禁值多少 |
| C 只开外环 | 关 | 进化 playbook 和 instinct | 软经验值多少 |
| D 双环协同 | 进化 | 进化，包括硬化和剪枝 | 协同是否大于两者之和 |

- 每组每题跑 3 次，模型用 1017 的 `fast` 档（关思考，更便宜，也更容易犯低级错误，提升更看得出来）；开思考的 `normal` 档作为补充对照。
- 预算：4 组 × 24 题 × 3 次 = 288 次运行，按每次 ¥0.1–0.5 估算约 ¥30–150；单次成本待 P0 实测。
- `python -m eval compare <A> <D>` 以题为单位配对比较，给出每题通过率差值均值的 bootstrap 95% 置信区间，分 evolve / held-out 报告，并列出低级错误失败数的变化。
- 外环只能看 evolve 的轨迹；门禁可以用 held-out 的汇总结果，但提案器看不到其中内容。头条用 held-out。

### 8.3 降低单次评测成本的手段

题目便宜之后，大部分进化迭代可以直接跑 evolve 切分（15 题 × 3 次，几元）。§8 早期版本里为 TB 设计的增量手段仍然有用，但从必需变成了优化：

1. **改动条件触发、局部生效**：探针和条目只在触发条件命中时才注入，所以没有触发的试验行为不变。
2. **L0 离线回放**：在已有轨迹上计算候选探针会在哪些试验里触发，在失败试验上触发的是潜在挽救，在通过试验上触发的是误报风险。不调用模型，先筛掉大部分候选。
3. **激活归因**：报告中把翻转的题分成「已归因」（轨迹里确实触发了某个改动，且方向符合契约预测）和「未归因」（没有改动被激活，只能是噪声），后者同时作为噪声对照组。

### 8.4 指标与目标

| 指标 | 说明 | 目标（是目标，不是承诺） |
| --- | --- | --- |
| 低级错误失败数 | 只挂陷阱检查的失败次数，A 组对比 B / D 组 | 接近 0 |
| held-out 通过率 | A → D，配对 bootstrap 95% CI | 置信区间下界大于 0 |
| 探针精确率、挽救率、破坏率 | 来自干预前后记录 | 破坏率接近 0 |
| 提案接受率、预测精确率 | 外环账本 | — |
| 每次成功的成本 | 与 A 组对比 | 不高于 A 组 |
| 整个实验的总花费 | 美元 / 人民币 | 在报告中明示 |

### 8.5 面试展示物

1. 一张主表：A / B / C / D 四组在 evolve 和 held-out 上的通过率（带置信区间）、低级错误失败数、每次成功的成本。
2. 按陷阱类别的前后对比：哪类低级错误被哪个环消灭了。
3. 一个完整的硬化案例：从失败簇到 instinct、条目、探针，附每一步的证据和数字。
4. （可选）TB4.1 20 题子集上基线和最终版本各一次的结果，作为外部旁证。

## 10. 风险

| 风险 | 缓解 |
| --- | --- |
| 统计噪声：held-out 只有 15 题 | 每题跑 3 次，按题配对做 bootstrap 置信区间；结合激活归因（§8.3）；不夸大 |
| 对 evolve 集过拟合 | RRSI 正则、held-out 隔离、OOD 检查、泄漏审查 |
| 探针误报拖慢运行 | 影子模式、精确率阈值、成本规则、结构剪枝 |
| 本地题是自己出的，可能被质疑「为方法定制」 | 题目先于探针冻结；每题有 near-miss 校验证明陷阱真实存在；类别来源写明出处；可选 TB4.1 子集做外部旁证 |
| TB4.1 子集结果被当成整个基准的成绩 | 对外统一说「TB4.1 的 20 题子集」，公开的全量成绩只作背景参照 |
| 挑题偏差 | 题目在运行前冻结，不按基线结果增删；TB4.1 子集只按元数据挑选 |
| 模型静默升级（`deepseek-flash` 不改名就换版本） | 每次运行记录模型标识；基线和最终运行之间换了版本就重跑基线 |
| 有些失败源于模型能力不足，而不是 Harness 的问题 | 只挂核心检查的失败不计入低级错误；挖掘阶段直接排除能力不足的簇（§6.2） |
| 探针被当作「作弊」 | 检查原语都是通用的，泄漏审查器加人工复核，每条探针在报告中列出来源证据 |
| 产品模式下没有判题器 | P5 的 Repo Gym；在那之前，产品模式只启用内环和人工批准的外环产物 |
