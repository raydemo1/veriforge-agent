# 记忆分类、主题聚合与更新评测

日期：2026-10-23。当前实现：`a77af51383e822dc034606f7d5a6d50f83c35aed`。

结论：普通显式更正可以工作，但语义冲突管理还不完整；当前没有稳定的内容分类和主题聚合。此次问题主要发生在旧事实发现、整体写入一致性和检索覆盖三个环节。

## 方法与边界

参考 [Chapter 3 用户记忆评估框架](https://github.com/bojieli/ai-agent-book/tree/main/chapter3/user-memory-evaluation) 的三层方法：直接回忆、跨会话消歧、跨会话综合。README blob 为 `3d5071ff53a21e2e1cf4b41398a11257a0410d65`；其中连续更正参考用例 blob 为 `7fb0e3fcd171fdb7db70233400b6a0840b0b9f64`。

采用原创编码场景，避免把银行预约等短期业务信息直接套入本项目“只保存长期偏好、规范、决定和可复用经验”的抽取策略。

- 9 组场景、22 次逐会话抽取、10 次独立回答，共 32 次真实模型请求，硬上限 36 次。无自动重试、无请求错误。
- 模型：当前 `fast` Profile，`deepseek-v4-flash`，thinking 关闭。
- 使用实际 `_claim_next_job → _process_job → MemoryService.write/search/format_hits` 链路，每个会话只提交自己的原始消息；下一会话抽取器只能通过已有记忆看到先前信息。
- 回答阶段只收到默认搜索结果，不带旧原始对话，不提供期望答案。固定 JSON 字段和答案别名用于确定性评分。
- 另做无需模型调用的检索对照和写入故障注入。
- 所有记忆、日志和故障均位于独立实验目录，没有读取或写入真实用户记忆。

这是一次有针对性的单次小样本诊断，不是参考仓库完整 60 题复现。没有使用独立 LLM 裁判，也没有运行带启动 Memory Index、`memory_read` 和主动搜索的完整 Agent，因此默认检索失败不能直接解释成完整 Agent 一定失败。抽取语言和自由文本主题可能随模型输出变化。

### 1. 语义更新没有完整解决

`background.py` 当前遍历 project、user 记忆后截取前 50 条，每条正文最多提供 300 字符。它不是按待更新事实相关性挑选，也不保证两个 scope 都有代表。

实验预置 50 条无关项目约定和一条用户旧报告格式。随后用户明确宣告新格式取代旧格式。抽取器看到的前 50 条全是项目约定，未见旧用户记忆 ID，因此新增了新格式，却没有 `supersedes`。最终：

```text
旧记录：REPORT_LEGACY_831，status=active
新记录：REPORT_MODERN_942，status=active，supersedes=null
```

此次回答模型根据新记录中“旧格式作废”的措辞选择了正确答案，但存储层仍保留两个有效记录。以后检索只召回旧条目时，仍有误用风险。

离线版本测试确认：旧 `expected_version` 会被拒绝。它解决指定 ID 的版本检查，不承担发现同义事实或语义矛盾的职责。

### 2. 文件级原子写入不等于整体更新原子性

`store.py` 先写新 Markdown，再改写旧 Markdown 使其退役。对第二次文件写入注入 `OSError` 后，观察到新旧两条记录同时 active。单个文件的替换是原子的，两文件构成的 supersession 操作没有整体事务保障。

这是可确定复现的故障路径，不代表真实运行中已经发生过该磁盘错误。

### 3. 默认检索既有数量边界，也有词汇边界

- 发布规范 8/8 存储成功。默认 `limit=6` 返回 6/8；同一查询在离线对照中增加返回上限后命中 8/8。因此此例直接遗漏来自返回数量上限，不能仅凭它证明必须采用某种聚类算法。
- 包管理器偏好被抽取器写为英文。中文查询 0/2，英文控制查询 2/2；增加上限仍不能修复中文查询的零命中。
- “简短答复还是长篇解释”命中风格偏好；“信息量和展开程度应该怎么控制”没有命中。增加返回上限同样无效。

这些对照不增加模型请求，也没有向回答模型补发正确记忆来重算成绩。

## 建议的最小设计方向

### 分类与主题分别承担不同职责

保留事实条目作为来源，增加少量明确元数据：

```yaml
category: convention       # preference / convention / decision / lesson
topic_key: orion/release
fact_key: release.build_command
scope: project
```

以上是建议字段，目前尚未实现。category 用于内容类型筛选；topic_key 用于聚合相关事实；fact_key 在同一作用范围和适用条件内定位可更新的具体事实。topic 展示标题仍可自然表述，不能把自由文本标题相同或路径重叠当作事实相同。

主题页由当前有效条目及其 ID、版本生成，是可重建的视图。条目更新后只刷新受影响的主题页；主题页不保存第二份可独立编辑的事实，也不把退役状态重新写成当前结论。先做分组和引用就能提供价值，无须每次再调用模型总结。

### 先发现相关旧事实，再决定写入动作

用候选事实的主题、字段和适用范围，从完整授权记忆库寻找相关旧条目，替换当前任意前 50 条的截取方式。仅增加总量上限仍会留下规模增长后的同类问题。

写入动作明确区分：重复则不新增；已确认的同一事实更正则替换；不同适用范围的例外并存；无法确定的矛盾保留待核验状态。项目例外不能退役个人全局默认，较新的设想也不能仅凭时间覆盖已确认决定。版本检查仍作为最后的并发保护。

新条目生效与旧条目退役需要共同的、可恢复的事务边界，完成后再刷新导航和检索索引。不能通过交换两次文件写入的顺序解决整体一致性问题。

### 主题检索后按预算展开事实

综合问题先定位主题，再按输入预算展开相关条目，必要时分页或继续读取。工具应明确返回是否还有未展示条目，不能让模型把前 6 条当作完整清单。

抽取时保留用户原始语言中的关键词，并维护主题别名；再用中文改写和中英文问题复测。向量检索或混合检索的收益需要另做有界对照，本轮结果只证明现有词汇检索的这两个具体遗漏。

优先顺序：旧事实发现与整体更新一致性 → 稳定分类和主题视图 → 主题展开及同义检索。每一步使用本次失败场景复测，并同时保留已通过的范围例外、未确认变更和部分更新用例，防止修一处退步另一处。
